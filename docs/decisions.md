# Decisions (ADR log)
Format: ID · status · decision · why · alternatives rejected. Append only; supersede, don't edit.

**ADR-001 · Accepted · Ship geometric analyzer v1 before Siamese v2**
- Why: no public dataset labels "muscle development per region". Geometry from silhouettes + keypoints works on day one and gives a baseline the Siamese net must beat.
- Rejected: Siamese-first (demo blocked on training), VLM-only analysis (non-deterministic, sends images out).

**ADR-002 · Accepted · BodyM as training data**
- 2,505 subjects, frontal+lateral silhouettes, height, weight, 14 measurements (bicep, chest, waist, hip, thigh, calf, forearm, shoulder breadth...). Silhouettes match our privacy design exactly.
- Licence: CC BY-NC 4.0 -> fine for portfolio/research, **not commercial**. Must be stated in model card and README. Commercial version would need own data or synthetic SMPL renders.
- Pairs for Siamese: any two subjects (A, B) -> target = m_A/h_A − m_B/h_B per region, a difference of height-normalised ratios (amended by ADR-032). ~6M possible pairs; sample per epoch.

**ADR-003 · Accepted · Silhouette-only upload**
- Raw RGB never leaves the device; server rejects non-binary images. Answers the "people feel uncomfortable undressing" problem and removes most data-protection risk.

**ADR-004 · Accepted · Siamese backbone = ResNet-18 (ImageNet), fine-tune**
- Silhouettes are low-information; 11M params is plenty; trains on M4 Pro MPS in minutes per epoch; ONNX on free CPU is fast.
- Ladder: linear probe on frozen features -> unfreeze last 2 blocks -> full fine-tune. Stop at the first rung that hits the gate.
- Rejected: DINOv2/ViT (overkill for binary shapes, slower CPU inference), EfficientNet (no clear gain, more fiddly on MPS).

**ADR-005 · Accepted · One agent + tools, no LangChain**
- Tools: `retrieve(query, filters)`, `get_gap_profile()`, `compute_volume(region, level, days)`, `check_safety(text)`. Direct OpenAI-compatible SDK so provider swaps are env-only.

**ADR-006 · Accepted · Siamese must beat "single regressor × 2 then subtract" baseline**
- If it doesn't beat it by a meaningful margin on held-out subjects, keep the simpler model and record the negative result. Honest negative results go in the README.

**ADR-007 · Accepted (amended by ADR-028: embeddings via ONNX Runtime int8, no torch in the API image) · Hybrid RAG = BM25 + bge-small-en-v1.5, RRF, numpy/FAISS-flat**
- Corpus is small (< 5k chunks). No vector DB. Exercise names need keyword match (BM25), intent needs semantics (dense).

**ADR-008 · Accepted (amended by ADR-028: cache state lives in Upstash Redis, not process memory) · Semantic cache keyed on sub-queries, not whole reports**
- Personalised reports are near-unique; caching them would serve wrong plans. Retrieval results per (normalised sub-query, namespace) are highly reusable.

**ADR-009 · Superseded by ADR-022, then ADR-028 · Deploy: Vercel (web) + HF Space Docker (API) + HF Hub (model)**
- All free. GitHub Pages rejected for web: no env vars / preview deploys; Vercel gives both.

**ADR-010 · Superseded by ADR-011 · Front view required, side view optional in v1**
- Front silhouette gives widths only; girths (arms, thighs) need side view. v1 marks girth-type regions as lower confidence without side view.

**ADR-011 · Accepted · 4-view guided turn capture (front, left, back, right) from video**
- User does one slow turn (~8 s) in front of the camera. Browser samples frames, estimates body yaw from keypoints (shoulder-width ratio + left/right landmark visibility), keeps the sharpest frame per view, and converts each to a silhouette. Still only silhouettes leave the device.
- Back/chest split: in a side silhouette, pixels in front of the shoulder–hip keypoint line = chest projection, behind = upper-back projection. Front/back width at armpit level = lat width (V-taper). Two sides -> left/right asymmetry.
- Limits: a silhouette sees outline, not definition. Trap/rhomboid/rear-delt detail and muscle separation are invisible; report says so. BodyM has front + side only, so the Siamese model uses those 2 views; back + second side feed the geometric analyzer (back width, asymmetry).
- Rejected: sending RGB for muscle-definition analysis (breaks ADR-003; no labelled data anyway).

**ADR-012 · Accepted · Body-fat % v1 = RFM from silhouette waist, shown as a range**
- RFM = 64 − 20·(height/waist) + 12·sex; validated vs DXA on NHANES (R² 0.75 men / 0.69 women). Waist girth comes from front+side silhouettes (calibrated on BodyM); a tape-measured waist, if entered, overrides it.
- Output a range (estimate ± measured error), never a single number. Known weak spot: lean people and older adults.
- Rejected: LLM estimating BF% (no grounding, hallucinates); scraped Reddit BF images (no consent, ToS risk, perceived labels, men only).
- See `docs/research/body-composition-research.md`.

**ADR-013 · Accepted (amends ADR-003) · On-device RGB model allowed; only scores leave the device**
- The muscle-definition model runs in the browser (ONNX Runtime Web, WebGPU -> WASM fallback) on the RGB frame. It outputs a 1–5 score per region; only those numbers are sent. The server still rejects any image that isn't a binary mask.
- Opt-in toggle ("analyse muscle definition on my device"); off -> report uses shape-only.

**ADR-014 · Accepted · Definition model = MobileNetV3-Small trained on MakeHuman synthetic renders**
- No public labelled real dataset exists. MakeHuman assets are CC0; muscle/weight sliders become labels. Render a grid (sex × muscle × fat × height × skin tone × lighting × fitted clothing) in Blender headless, ~30k images, 4 views.
- Labels: per-region definition 1–5 derived from (muscle slider, fat slider) via a fixed mapping. Real fine-tune + validation on a consented set (ADR-016).
- Gate: Spearman ρ ≥ 0.5 vs blinded human ratings on the real set. Below that -> feature ships as "experimental" or is cut; negative result documented.
- Rejected: ResNet-50/ViT (too heavy for phones), cloud VLM (breaks privacy; free hosts may train on prompts).

**ADR-015 · Accepted · Energy targets: Mifflin-St Jeor × activity factor, with safety floors**
- Most accurate common RMR equation (≤ 10% error for 78% of subjects). Katch-McArdle not used: needs measured lean mass.
- Goals: cut / recomp / bulk as ranges. Exact floors and caps live in `privacy-and-safety.md` (single source of truth).
- Supersedes the "no calorie targets in v1" line in `privacy-and-safety.md`.

**ADR-016 · Accepted · Real validation set = consented volunteers with tape measurements**
- 20–40 adults (mixed sex/BMI), signed consent, 4-view capture + tape (waist, neck, hip, arm, thigh) + 3 blinded raters scoring definition 1–5. Stored offline, encrypted, deleted after the project. Used for evaluation and a small fine-tune only.
- Optional: a gym BIA/DXA reading where available as a stronger BF% reference.

**ADR-018 · Accepted (amends ADR-016) · No scraping; real set is not a demo blocker**
- The demo (P0–P7) needs no real labelled photos: BF% is RFM, definition model trains on synthetic data (ADR-020).
- P8 real data: own scans + tape measurements, consenting friends, openly licensed images (Wikimedia Commons CC0/CC BY, licence logged per image).
- Rejected: scraping r/guessmybf etc. — no consent for semi-nude body photos, Reddit's terms restrict ML use of its data, labels are guesses, almost all male.

**ADR-019 · Accepted · "On-device" = the user's browser on any device**
- Laptop webcam, phone camera or file upload all work; MediaPipe and ONNX Runtime Web run in Chrome/Safari/Edge on desktop and mobile. Live webcam preview is supported.

**ADR-020 · Accepted (amends ADR-014, ADR-018) · Definition model is part of the demo, trained on synthetic data only**
- Muscle definition is a core feature, so it ships in Track A (P4), before the demo deploy.
- Demo training data: MakeHuman synthetic renders only (+ BodyM for silhouettes). Real data (own measurements, Wikimedia Commons) arrives in P8.
- Demo gate is on synthetic held-out data + a logged sanity check on own scans; UI carries an "experimental — trained on synthetic data" badge until real-data ρ ≥ 0.5 (P8).
- Risk accepted knowingly: synthetic-to-real gap. Mitigation: same browser preprocessing on renders, background swap, heavy augmentation.

**ADR-021 · Accepted (supersedes ADR-001 ordering) · Siamese CNN before muscle definition, both before demo deploy**
- Order: P2 BodyM + geometric baseline -> P3 Siamese CNN -> P4 definition model -> P5 RAG -> P6 agent -> P7 deploy.
- The Siamese CNN is the core model and ships in the demo. Geometric analyzer stays as baseline A, fallback, and for back view + asymmetry (BodyM has no back view).

**ADR-017 · Accepted · Free LLM providers, text only**
- Primary: Groq `openai/gpt-oss-120b` (~30 RPM, 1,000 req/day free). Fallback: OpenRouter free endpoints with `data_collection: "deny"` / no-train hosts. Provider + model in env; one OpenAI-compatible client.
- LLMs never receive images; they receive the GapProfile, BodyComp numbers and retrieved text.
- Budget: ≤ 3 LLM calls per report (route only if embedding router is unsure, write report, safety rewrite if flagged). Semantic cache keeps repeat traffic off the quota.
- Embeddings run locally (bge-small) — no API dependency.

**ADR-022 · Superseded by ADR-028 (had superseded ADR-009) · No HF Space / HF Hub; API and models run locally**
- HF Docker and Gradio Spaces are not free for this account (static Spaces cannot run FastAPI). Decision (user, 2026-11-01): drop HF Spaces and HF Hub for now. API (`uvicorn`) and ONNX/torch models run on the laptop; model cards live in `ml/`.
- Web stays on Vercel (free). Calling `http://localhost:8000` from the Vercel page works in Chrome/Edge, not Safari. Day-to-day dev runs the web locally.
- Consequence: the P7 gate "stranger completes the flow from a public URL" is blocked until public API hosting is chosen (candidates: Cloudflare Tunnel to the laptop, a free Render/Fly service). Decide at P7 start; the `Dockerfile` is kept for that.
- No HF token needed; `deploy-space.yml` removed. Privacy model unchanged (silhouettes still never include RGB; the API now just runs on the user's own machine).
- Rejected: Gradio-wrapper workaround (not free either), paid hardware.

**ADR-023 · Accepted (amends P1 task list, refines privacy-and-safety.md) · Browser capture design**
- Segmentation: the **Pose Landmarker's own mask** (`outputSegmentationMasks`), one model and one pass. No separate Image Segmenter. Trigger to add it: masks with holes, background blobs or missing limbs on the review screen.
- Mask frame: crop from the **full-body** bbox (+5% margin), letterboxed into 384x512 (W x H), then the head is removed, so the head-top stays a height reference in the keypoints. Keypoints are remapped to that frame and clamped to [0,1]. Head cut row = `shoulderY - 0.4 * (shoulderY - earY)` (tunable in `capture/config.ts`); the privacy doc's "above the shoulder keypoint line" would shave deltoid/trap tops, which sit above the joint.
- Mask PNG: 8-bit, 1-channel, values {0,255} via `fast-png` (`canvas.toBlob` can only emit RGBA). Meets the server check "1 channel, only {0,255}"; not packed 1-bit, size is irrelevant at this resolution (2-4 KB).
- Assets self-hosted (`public/models/pose_landmarker_lite.task`, `public/wasm` copied from `node_modules` at `predev`/`prebuild`): no third-party request during capture.
- View matching is **user-paced**: body angle from shoulder-width / torso-length (pixel units, so distance and aspect cancel) against a median "square to the camera" reference learned in the countdown, cross-checked with the shoulder depth gap. Fixed turn order (front, left, back, right) separates front from back and left from right; face visibility and far-shoulder visibility are debug-only. A hold bar fills while the pose matches; **Capture now** is the manual fallback.
- Rejected: fixed time slots per view (no cue, silent misses); visibility-based "full body" and left/right tests (far limbs and the face are legitimately hidden in profile and back views).

**ADR-024 · Accepted · Geometric analyzer: silhouette-only landmark rows, two scales never mixed, null-model gate**
- Rows: BodyM has no keypoints, so rows come from the mask alone, one code path for BodyM and browser masks. Run-length analysis: central run = torso; crotch = where the central run splits; armpit = where arm runs merge into the torso; neck = narrowest row in the top ~25%; waist = narrowest torso row between armpit and crotch; hip = widest row between waist and crotch. Side-view rows where arm and torso runs merge are skipped. Search windows are tuned on the BodyM train split only. Keypoints are used for view selection and a logged sanity check only.
- Two scales: (1) the gap (`GapProfile.delta`) uses scale-free silhouette features divided by silhouette height, for both goal and current; a goal photo has no weight, so no weight-aware model touches it. (2) Absolute cm (waist for RFM, `BodyComp`) uses a regressor on silhouette features + height + weight + sex, for the current person's own scan only. Test: the gap is identical when only the profile weight changes.
- Null model: every silhouette claim is reported next to a ridge on [height, weight, sex] only. A gate counts only where the silhouette model beats it (waist and hip correlate strongly with weight alone, so a bare ρ gate can pass without the silhouette adding anything). Applies to the per-region ρ gate and to waist MAE.
- Labels: only 8 regions have BodyM ground truth (shoulders, chest, waist, hips, upper_arm, forearm, thigh, calf). `upper_back` and `lats` are geometric-only and outside the ρ gate.
- Rejected: MediaPipe on BodyM silhouettes (unreliable on binary masks, a second code path); a weight-aware regressor inside the gap (goal has no weight, mixes scales).

**ADR-029 · Accepted (amends ADR-024 gate) · Gate 2 criterion changed after the first result**
- Numbering note: first written as a second "ADR-025" (the goal-photo ADR landed in parallel); renumbered 2026-11-01. Nothing else refers to it by number.
- Original gate (ADR-024): silhouette-only feature must beat the weight-aware null ridge on >= 6 of 8 regions. First run, testA (87 subjects): **1/8** (waist only, interval includes 0). Null rho 0.80-0.93 on every region: height, weight and sex alone predict BodyM measurements/height very well. The comparison was unlike-for-like (weight-free vs weight-aware), so it could not pass.
- New criterion, decided by the user on 2026-11-01 after seeing val and testA: (a) silhouette-only rho >= 0.6 on >= 6 of 8 labelled regions (the gap is weight-free, ADR-024), and (b) the silhouette adds signal beyond the null: (combined - null) rho with a 95% subject-bootstrap interval excluding 0 on >= 6 of 8.
- First-run state for the record (testA): (a) 5/8 (shoulders .79, chest .85, waist .91, hips .83, upper arm .76; forearm .15, thigh .40, calf .46); (b) not yet bootstrapped.
- Because the criterion moved after seeing testA, all feature changes are tuned on val only, and the final numbers are reported on testA and testB together.
- Known weak spots: forearm, thigh, calf (arm width depends on A-pose angle; a hand in front of the thigh inflates side depth; 26% of side masks are clipped, so girths are missing for 12-29% of subjects).

**ADR-025 · Accepted (amends ADR-011 for the goal input; revives ADR-010's idea for the goal side only; extends ADR-013) · Mode 1: goal photo, front-only by default, priority for P7**
- Goal photos are usually front-only; the current scan keeps all 4 views. Goal side view is optional.
- Siamese (P3): train with **side-view dropout**, randomly blanking the goal's side input, so a front-only goal is an in-distribution input. Girth regions (upper_arm, forearm, thigh, calf, chest depth) get lower confidence when the goal side view is missing (on top of MC dropout, calibrated on the slice below). The P3 gate report adds a **front-only slice on BodyM Test-B**, with baselines A and B run on the same slice and full-input numbers beside it.
- Definition (P4): the in-browser model also scores the goal photo (RGB stays on the device, ADR-013, only scores leave). The report compares definition and adiposity, goal vs current. Regions a front photo cannot show (back) are `N/A` for the goal.
- Labelling: every goal-photo-derived score is shown as **"appearance-based"** (pose, pump, lighting, edits). Warn, don't block, if the full body is not in frame: a cropped body breaks the height normalisation behind every scale-free feature (ADR-024). Reuse the P1 mask edge-contact check and show its number (see mistakes.md, 2026-11-01).
- Realism flag: compare the goal's **shoulder-to-waist ratio** with the ratio the user's own frame allows, because bone width cannot change. Ratios, not widths, so the goal person's size does not matter. Formula and threshold are fixed in P6 from `evals/safety.jsonl`, not guessed here.
- Rejected: requiring a side-view goal (most goal photos don't have one, and the flow would stall); a separate front-only model (two models to ship; dropout gets it from one); hiding the girth-confidence drop (users should see why arms and thighs are less certain).

**ADR-026 · Accepted (amends ADR-005, ADR-017) · Mode 2: "describe your goal" via text -> archetype table, built after the deploy**
- Scope and timing: **P9, after P7 is live; must not delay P7.** The one pre-deploy requirement lands in P4: save every render's parameters (sex, muscle, fat, height, proportions) in `synth/params.csv` and its 4-view masks next to the images, so P9 reuses them and nothing is re-rendered. Masks come from the same segmentation + crop + head removal as real input, run on the clean render, so archetype proportions are comparable with user scans.
- P9 builds an offline **archetype table** from those renders: region proportions via the geometric analyzer (scale-free, ADR-024) + definition labels from `labels.csv`.
- New agent tool `goal_from_text` (**text only, never images**): extracts a pydantic-validated goal (sex, build, muscle level, fat level, region emphasis), confirms the interpretation with the user, applies the same safety floors (no target BF below the sex floor, `privacy-and-safety.md`), then looks up the table -> target `GapProfile` + target definition scores -> the same report and plan flow as Mode 1 (so the realism flag and safety layer apply unchanged).
- Named people become descriptors only ("lean, athletic, defined"). The agent never states a real person's body stats.
- Consequences: (1) a Mode 2 gap is geometric-analyzer quality (baseline A), not Siamese, and its confidence is set accordingly; (2) the extraction is an extra LLM call, so Mode 2 reports may use up to 4 calls where ADR-017 allows 3; (3) the user's goal text reaches the LLM provider, so it gets the same PII normalisation as plan queries and is never logged beyond the intent label (`privacy-and-safety.md` needs a one-line note when P9 starts).
- Rejected: an LLM stating target measurements directly (ungrounded, may quote real people's stats); re-rendering in P9 (cost, delays); sending any image to the LLM.

**ADR-027 · Accepted · Goal step UI: two tabs; Mode 2 preview is a static pre-rendered library**
- The goal step has two tabs: "Upload a goal photo" (default) and "Describe your goal". P7 ships the tab structure with only the upload tab live; P9 turns the second on.
- Preview (P9): a library of ~300–500 pre-rendered front+side images (neutral grey, fitted clothing, no face detail, compressed), served as static assets. The UI shows the render nearest to the parsed goal, and "more muscle / leaner" sliders swap previews client-side. No live rendering, no server cost. Labelled as an illustration of the described goal, not a prediction of how the user will look.
- Stretch, optional and only after the P9 core passes: live 3D preview in three.js with muscle/fat morphs.
- Rejected: live server-side rendering (cost, latency, nothing free to host it, ADR-022); making the three.js preview part of the core (large scope for a nice-to-have).

**ADR-030 · Accepted (refines ADR-023 and ADR-024; builds on ADR-029) · Canonical frame, row finder and features as built in P2**
- Canonical frame (`ml/src/preprocess.py`): browser masks (384x512, head-less) pass through unchanged (`from_browser`: validate, largest component), because re-cropping a head-less mask would rescale the body. BodyM full-body masks go through `from_bodym`: the browser's exact crop and letterbox, then a neck cut. Body height in the frame is `2 * (feet_row - 256)` (the letterbox is centred), so no keypoints are needed. `NECK_CUT_OFFSET = 0.0`: parity on 3 captures, |z| <= 1.9 on the head cut; phone captures cut higher, left to P3 cut-row jitter augmentation.
- Row finder (`analyzer/rows.py`), no centre column: armpit = first row with >= 3 runs held 5 rows; crotch = first row in 0.45-0.65 of body height where the widest run drops below 65% of its maximum since the armpit, held 8 rows. This replaces "where the central run splits" from ADR-024 (the centre column drifts with lean: found 66.8% of BodyM crotches, now 98%). Outside 0.45-0.65 the crotch counts as not found and a prior is used: shorts hide it (hem gap measured 0.667-0.694 vs BodyM 0.583 +/- 0.028). Waist and hip come from the widest-run profile.
- Features (`analyzer/features.py`), all divided by the view's own body height: girth = ellipse from front width and side depth (chest, waist, hip); arm thickness = area / path length, independent of the A-pose angle (upper arm window 0.00-0.07 below the armpit); thigh and calf use the peak front width (side depth hurt them: hands in front of the thigh, clipped feet); shoulder row = armpit - 0.07. Windows swept on train (`ml/src/sweep_windows.py`), checked on val, reported on testA and testB.
- Forearm: the upper-arm window also scores rho 0.78 against forearm circumference, but that is general arm size. Rejected as the forearm feature; the forearm keeps its own window (rho ~0.3) and near-zero confidence.
- Clipped BodyM side masks (26% touch the bottom edge, random in sex and height): excluded from every side-view fit and eval.
- Confidence per region = clip((rho_val - 0.3) / 0.6, 0, 1), times 0.7 per row-finder fallback; `upper_back` and `lats` (back view, no label) are fixed at 0.3. Left/right asymmetry is not implemented (no ground truth to validate it).

- For the deploy spike: the API imports `ml/src/preprocess.py` (so the image must carry the `ml` package files it needs) and `scipy.ndimage` (ADR-028 asks the spike to measure its cost).

**ADR-032 · Accepted (amends ADR-002 and ADR-024's target wording; user decision 2026-11-01) · Siamese and baseline target = proportion gap, difference of ratios**
- Target: `delta = m_A/h_A - m_B/h_B` per region, `m` = the BodyM measurement mapped to the region (`ml/src/data/regions.py`), `h = height_cm` (not the tape `height` column). A = goal, B = current; positive = goal larger (same sign as `GapProfile.delta`). This is what baseline A already estimates (`fit_gap.py` fits `m/height_cm`), so A, B and the Siamese are scored in the same units.
- Why not `(m_A - m_B)/h` with one height: the canonical silhouette removes absolute scale and `compare()` receives no height; a goal photo has no height at all.
- Consequence 1: `delta` is a **proportion gap**. It answers "how much bigger would your chest be, relative to your height, if you had the goal's proportions". The UI converts it to cm as `delta x the user's own height` and labels it "at your height".
- Consequence 2: the Siamese net never sees height at inference, so it cannot learn a height-dependent shortcut. Baseline A and baseline B use the same definition.
- Rejected: shared or mean height in the denominator (needs an input the goal lacks; baseline A would need refitting).

**ADR-033 · Accepted (amends ADR-006 and ADR-025's region lists; user decision 2026-11-01) · P3 gate protocol, written before Test-B is scored**
- **Pass rule.** For each baseline separately (A, B), the 95% subject-bootstrap CI of `MAE_baseline - MAE_siamese` is > 0 on >= 6 of 8 regions (forearm may be one of the 2 misses). **Fail regardless of the count** if on any region that CI lies entirely below 0 (significantly worse).
- **Front-only slice** is a separate gate on the same rule, against **width-only baseline A** (not the 2-view baselines).
- **Bootstrap unit.** Resample subjects with replacement; each pair is weighted by `mult(A) x mult(B)`, the multiplicities of its two subjects in the resample; MAE per region is the weighted mean; seed fixed.
- **Pair list.** Seeded, subject-level, generated once from Test-B, committed, hash logged before any model is scored on Test-B; identical for A, B, Siamese and both slices. Test-B has 399 subjects (the subject shared with Test-A is dropped); the pair count is fixed by the generator and recorded here once generated (placeholder: **N = TBD**).
- **Power check** (before scoring, on val with a same-size pair list): the smallest MAE difference the pair count can detect, per region, reported next to the gate. A region whose detectable difference exceeds the baseline gap is marked underpowered in the gate report, not silently counted.
- **Test-B discipline.** Scored once per final candidate. Tuning and rung choices use val only. `evaluate.py --test-b` keeps a ledger of model hashes and refuses a second run for the same hash; each Test-B look is logged in `dev-log.md`; a second look needs a new ADR.
- **NaN handling.** Baseline A returning NaN features is masked and its coverage reported; it is never counted as `delta = 0`.
- **Region groups (code is the single source).** Width-only (front view suffices): shoulders, upper_arm, forearm, thigh, calf. Side-dependent: chest, waist, hips (ellipse girth needs depth). ADR-025's "girth regions" list (arms, thighs, calves, chest depth) does not match the geometric features as built; the gate report uses these two groups. The Siamese front-only confidence is calibrated per region, so arms and legs get no blanket penalty.
- **Fail path.** Not beating baseline B -> ADR-006 negative result; ship the better model and document it.
- Confidence for the Siamese is the per-region residual std on val (separately for the full-input and front-only slices), not MC dropout (user decision 2026-11-01).
- **Pair list as built (2026-11-01, `ml/src/data/pairs.py`).** Resolves "N = TBD" and replaces "seeded sampled pair list" with something simpler: the list is **every ordered pair (goal i, current j), i != j, of the Test-B subjects that have a photo with an unclipped side mask**, one seeded canonical photo per subject (the same photo for the full-input and front-only slices). Test-B: 351 of 399 subjects qualify (48 have only clipped side masks and are excluded), **122,850 ordered pairs**, manifest `evals/testb_pairs.json`, hash `9abfd0c74c1f6456c25c977697fa7df64124b64cc219849404c411ec4afb211e`. No pair sampling remains, so the bootstrap is exact matrix algebra (`w^T E w`). Power-check constant: the CI half-width must be <= 10% of the baseline MAE to count a region as adequately powered (my choice, not data-derived). Subjects with only clipped sides are a coverage limit for the gate, stated in the model card.
- **Amendment (user decision 2026-11-01).** Baseline B is one regressor trained with the same goal side-blanking as the Siamese, not a separate front-only network, so the comparison is a like-for-like ablation of the pairwise head.
- **Amendment (user requirement 2026-11-02; option chosen by Claude, open to the user's veto, before any Test-B scoring of a neural model).** The final candidate runs 3 seeds and the spread per region is reported separately; the seed that goes to Test-B is the best on val. No ensemble: three ResNet-18s would break the 50 MB and 75 ms limits for the shipped model. The gate rule (subject bootstrap) does not change.

**ADR-036 · Accepted (user decision 2026-11-02; amends ADR-011 and ADR-024 for `lats`, and ADR-035 integration item 3 for `lats`; supersedes the earlier chat instruction "lat flare / upper-back thickness, unranked", which was never in an ADR) · `lats` = ANSUR II ridge on baseline B's chest, shoulders and waist; written before any ANSUR file is downloaded or fitted**
- **Why.** Lats are a priority region: they cannot be excluded or assumed. BodyM has no back-width label and its release has no meshes. ANSUR II has a tape-measured back width, `interscyei`. My earlier claim that no standard lat measurement exists was wrong (mistakes.md).
- **Chain.** silhouette -> baseline B (unchanged, not retrained) -> per-person chest/h, shoulders/h, waist/h -> ridge fitted on ANSUR II -> interscye/stature -> lats gap = ridge(goal) - ridge(current). The ridge never sees pixels (the public ANSUR II files hold no images).
- **What it is not.** After B no new image information enters. With the same sex on both sides the lats gap is a fixed linear combination of the chest, shoulders and waist gaps, `w_c*d_chest + w_s*d_shoulders + w_w*d_waist`. It estimates back width from build, not from the lat muscles, and in the priority ranking it partly double-counts those three regions. The README says so.
- **Model form (fixed now).** Inputs: chest circumference/stature, shoulder breadth/stature, waist circumference/stature, `is_male`. Target: `interscyei`/stature. Ridge, additive sex term, no interactions, alpha from a fixed grid chosen on the validation fold only. `is_male` is the profile sex of the user, used for both goal and current (a goal photo has no sex label), so it cancels in the gap. All ratios are to stature so a goal photo with no height works. Coefficients in raw units go to a small JSON (like `gap_coef.json`) together with the sigmas and the verdict below.
- **Data.** ANSUR II public files, one CSV per sex, from Penn State OpenLab: `https://tools.openlab.psu.edu/publicData/ANSUR_II_MALE_Public.csv` and `.../ANSUR_II_FEMALE_Public.csv`; 4,082 men + 1,986 women = 6,068 (MFR NATICK memo 14 Apr 2017, para 3); millimetres; `subjectid` is unique per participant (MFR para 4), so a row split is a subject split (the script asserts it). Saved to `ml/data/ansur/` (gitignored). Downloaded in P3 by explicit user decision: an exception to the CLAUDE.md rule "datasets only in the phase that needs them".
- **Licence (checked 2026-11-02).** The OpenLab ANSUR II and data pages state no licence, terms of use or citation request. What exists: the MFR says the databases and memo "have been reviewed and cleared for UNLIMITED PUBLIC RELEASE" (para 1), the handbook and summary report say "Approved for public release; distribution is unlimited". That is a release statement, not a licence, and I am not giving a legal opinion. Use here: research and portfolio. We do not redistribute the CSVs; only a handful of fitted coefficients ship. Cite Gordon et al. 2015, "2012 Anthropometric Survey of U.S. Army Personnel: Methods and Summary Statistics", NATICK/TR-15/007. If a commercial version is ever planned, ask the POC named in the MFR first. MFR para 7: the two databases "should be treated and analyzed separately" because a pooled sample represents no real population. We pool only to fit relationships (with a sex term) and report per-sex R²; the pooled mix says nothing about prevalence.
- **Definitions (Measurer's Handbook NATICK/TR-11/017; PDF page = printed page + 10).**
  - `interscyei` = Interscye I, 6.4.55, printed p.131: "The distance across the back between the right and left posterior axillary fold landmarks." Standing, steel tape in a straight line (not arching over the shoulder blades), at maximum quiet respiration. **This is the back width we want.**
  - `interscyeii` = Interscye II, 6.4.56, p.132: distance between the right and left **midscye** landmarks. Midscye (5.2.34, p.56) is halfway along the line from the posterior horizontal scye to the acromion, i.e. higher, toward the shoulder tip. Not used.
  - `chestcircumference`, 6.4.25, p.101: "maximum circumference of the chest at the fullest part of the breast", at the right chest point anterior (a dot on the bra for women); footnote 7: ANSUR I took males at nipple level.
  - `biacromialbreadth`, 6.4.9, p.85: distance between the right and left acromion landmarks on the tips of the shoulders; **sitting**, beam caliper.
  - `bideltoidbreadth`, 6.4.12, p.88: maximum horizontal distance between the lateral margins of the upper arms on the deltoid muscles; **sitting**, beam caliper; deltoid landmarks not used.
  - `waistcircumference`, 6.4.88, p.164: horizontal circumference at omphalion (centre of the navel), standing. `stature`, 6.4.76, p.152: standing surface to top of head, Frankfurt plane.
- **BodyM side (arXiv 2210.05667, sections 3.2 and 4).** Each of its 14 measurements is "the lengths of curves traversing pre-specified vertex paths on the mesh", summed vertex to vertex, on SMPL meshes in A-pose. The paper names shoulder-breadth, chest girth and waist girth but gives no landmark, level or path type for any of them, and no height definition. So the shoulder column cannot be chosen from the definitions alone.
- **Shoulder column rule (fixed now; uses inputs only, never the lats target).** Default `biacromialbreadth` (skeletal tip-to-tip, no muscle bulge; my reading of what a mesh shoulder path measures, unverified). `ml/src/ansur_check.py` prints, per sex, the mean of BodyM `shoulder_breadth`/`height_cm` next to ANSUR biacromial/stature and bideltoid/stature (and chest, waist). Switch to `bideltoidbreadth` only if BodyM's mean is closer to bideltoid's than to biacromial's for both sexes. The output goes into `dev-log.md`. Chest and waist have one ANSUR candidate each: their gaps are reported, not acted on.
- **Split and noise (fixed now).** Seed 0, stratified by sex, 70/15/15 train/val/test by subject. Noise: B's predictions replace tape values at inference, so inputs get independent Gaussian noise with the per-region val residual std of B's per-person prediction (`gap_regressor.json`, `sigma_full`; same units, measurement/height): chest .0182, shoulders .0056, waist .0194; front-only goal (`sigma_front`): .0215, .0058, .0206. `is_male` and the target get no noise. Training: 20 noisy copies of every train row, fresh noise each. Alpha: chosen on val with noisy val inputs. The test split is scored once, after alpha is fixed, in the same run that writes the JSON.
- **Metrics reported (test split).** (1) MAE in interscye/stature units (cm at 175 cm only as a reading aid). (2) R² on clean inputs: the shipped (noise-fitted) ridge, plus a clean-fitted ridge as the ceiling of what build explains. (3) R² on noisy inputs at `sigma_full` (50 seeded draws per subject, pooled), with a 95% test-subject bootstrap interval. (4) Incremental R² over chest girth alone: a ridge on [chest/stature, is_male] under the same protocol (chest noise only), clean and noisy; no threshold, it decides the README wording. (5) Per-sex R², clean and noisy. Informational only, never the verdict: noisy R² at `sigma_front` and at 1.5 x `sigma_full` (B's error was 31-55% larger on Test-B than on val, ADR-035; the 1.5 is my stress factor).
- **Pre-registered rule.** `lats` becomes a ranked region only if the held-out **pooled noisy-input R² (point estimate, `sigma_full`, shipped model) >= 0.5**. Pass: lats join the priority ranking. Fail: lats are still shown, with the (low) computed reliability, excluded from the priority ranking, and the README says why. The verdict, the numbers and the rule are stored in the coefficient JSON and the ranking reads the verdict from there. If pooled passes but a per-sex noisy R² is below 0.5, the verdict still stands as written and the README shows the per-sex numbers. Reading aid: with `reliability = 1 - sqrt(s_goal^2 + s_current^2)/s_prior` (ADR-035) and `s_prior = sqrt(2) x` the std of the true target, a noisy R² of 0.5 corresponds to a reliability of about 0.29, so even a pass is a low-reliability region. **No tuning after the result without a new ADR.**
- **Integration (built after the verdict).** `lats` is computed in `SiameseSubtractAnalyzer` from B's goal and current per-person outputs: `goal_ratio`/`current_ratio` carry the interscye/stature estimates, `delta` their difference. `measured` is false if any of chest, shoulders, waist is not measured. Reliability: `s_goal` and `s_current` are the residual std of the ridge on noisy held-out inputs against the clean target, with the front-only sigmas for a front-only goal (so a front-only goal returns a lat gap at lower reliability); `s_prior` is the std of the true gap over ordered held-out pairs. The geometric back-view `lats` is retired. `upper_back` is unchanged (geometric, back view, unranked, confidence 0.3) until the user decides whether its size number stays; the back view otherwise keeps pose quality and asymmetry, because a back silhouette is the mirror of the front outline and adds no size information. V-taper (shoulder / waist) stays a derived, ranked metric. P6: the planner treats `measured: false` lats as "not measured", never "on target". Plan changes (P4, P8, P6) and UI/model-card text are written in the next step of this work, not here.
- **Limitations, stated up front.** (1) An inference from build (chest, shoulders, waist), not a direct look at the lat muscles; two people with equal ratios get equal lats whatever their training. (2) A chain on B's outputs: B's errors enter the ridge. Simulated noise is independent and Gaussian at val level; real B errors are correlated across regions (chest and waist share a silhouette) and larger on in-the-wild masks, and ANSUR people have no silhouettes, so B has never been run on them. (7) The image-to-lat link is not validated by this ADR: P4 adds a mesh-computed interscye label on synthetic renders (synthetic only, the README says so) and P8 adds tape-measured interscye on consented volunteers. **ADR-038 · Accepted (user decision 2026-11-02; items marked "mine" are my additions, open to the user's veto; builds on ADR-032, ADR-035, ADR-036) · Frame V-taper: index = shoulders_ratio / waist_ratio from B's per-person outputs**
- **Definition.** Per person, `index = shoulders / waist`, both B's per-person outputs (measurement / `height_cm`, ADR-032 units; `shoulders` = BodyM `shoulder_breadth`, `waist` = waist circumference). A breadth over a circumference, so the value is about **.40** (BodyM means .2131 / .5280 male, .2029 / .5180 female, `ansur_check`). It is not the gym ratio: **no "/ 1.618" score and no "ideal" line anywhere.**
- **Shown.** Goal index, current index, and `delta = goal - current` (same sign as `RegionGap.delta`: positive = the goal has the stronger taper).
- **Where.** A separate `GapProfile.v_taper` field (goal_index, current_index, delta, reliability, measured), **not an 11th region**: `REGIONS` and the all-regions check are unchanged and `RegionGap` keeps its meaning (proportion gap). The field is `None` when the analyzer gives no per-person ratios (the geometric fallback, ADR-035), and `measured: false` with no numbers when shoulders or waist is not measured (mine; follows `RegionGap`).
- **Label.** UI, README and report say **"frame V-taper (estimate)"**. One-line definition for the agent (P6): "shoulder breadth over waist circumference, from build and silhouette; frame, not deltoid size". Why "frame": BodyM's shoulder column is closest to `biacromial` (bone width, `ansur_check`), so deltoid size does not enter.
- **Reliability (val residuals only).** Same formula as ADR-035: `clip(1 - sqrt(s_goal^2 + s_current^2) / s_prior, 0, 1)`. `s_goal` and `s_current` = residual std of the index on val (B's predicted ratio vs the true `shoulder_breadth / waist` from the labels), with the front-only slice for a front-only goal; `s_prior` = std of the true index gap over val ordered pairs. Model: B full seed 0, hash 213383d7c86f, val 251 subjects. **No Test-B look at all:** Test-B is B's one look (ADR-033, ledger), and the ratio is never scored there. Stored under a `v_taper` key in `gap_regressor.json`, written by a small script from a val prediction pass; **the ONNX is not re-exported** (user decision). Provenance (user condition): the block records the script's git commit hash and whether the tree was clean, the checkpoint `model_hash`, and the SHA-256 of the ONNX file the analyzer loads. The top-level `model_hash` in that JSON is the SHA-256 of the **checkpoint** (ADR-035), so it covers neither the ONNX nor the JSON: "model hash unchanged" does not by itself prove the ONNX is unchanged, and the stored ONNX hash does. A test checks that the block's `model_hash` equals the top-level one. The block carries its own `version`, so the JSON is versioned apart from the model. Independent shoulder and waist errors are assumed (one silhouette makes them probably correlated; the effect on the ratio is unknown); val also picked the epoch, so it is slightly optimistic.
- **Limitations, stated up front.** (1) The index is **mostly waist**: relative spread across people is about 14% for waist and 5% for shoulders (`sigma_prior / sqrt(2)` over the mean ratio, `gap_regressor.json`), so the index gap largely repeats the waist gap. (2) Frame, not deltoids (above). (3) Shoulders are B's weakest region (reliability .50 / .49, ADR-035 export). (4) A loose top reads wider at chest and waist (own-scan check: +5 to +6 cm). (5) Disclosed, not tested: BodyM's shoulder path definition is unknown (ADR-036).
- **Ranking (user confirmed 2026-11-02; amends ADR-036's "ranked").** V-taper is **shown, not ranked**. Entering the priority ranking later needs a new ADR.
- **Decision rule for a planner input, fixed before it is computed (threshold mine, approved with two conditions by the user).** Per sex `s`: over the val **same-sex ordered pairs** (the pairs `sigma_prior` uses: 251 val subjects, one canonical photo each), regress the true index gap on the true waist gap (OLS with intercept, linear) and take `unique_share_s = 1 - R^2_s`. **Noise-free:** both gaps come from the ground-truth BodyM ratios (`shoulder_breadth / height_cm`, `waist / height_cm`), no model output, because B's shoulder noise is large against the real shoulder spread and predicted inputs would pass on noise. The statistic is `unique_share = min(unique_share_male, unique_share_female)`. After M2: **`unique_share >= 0.2`** keeps the index gap as a planner input (P6); otherwise it stays display-only and the planner input is dropped. Definition, threshold and both conditions are fixed here; computed once; no change to the threshold after the run. Expectation written first (user's estimate): with independent shoulders and waist the shoulders would be about 10% of the index-gap variance (spreads of 5% and 14-15%), so a drop is the likely result, and a legitimate one.
- **Out of scope here.** The reachable ceiling (M2) gets its own ADR when it starts: BF-floor range, RFM inversion and the one-sided realism flag.
- Rejected: any score out of 1.618; a width ratio read straight off the silhouette (baseline A's shoulders are worse than B's on Test-B, .0107 vs .0083, and clothing moves its rows); an 11th region; scoring the ratio on Test-B.

**ADR-040 · Accepted (user decision 2026-11-02; items marked "mine" are my additions, open to the user's veto; builds on ADR-038 M2, ADR-037 Amendment 4, ADR-012 RFM) · Reachable frame ceiling: V-taper index the user's own frame allows, from RFM inverted at a pre-registered body-fat range**
- **Why.** Bone width cannot change, so a goal index above what the user's shoulders allow at a lean waist needs something a silhouette cannot measure. The flag must never claim what the planner will not plan, so its lower body-fat limit is the same constant as the planner's deficit floor.
- **Formula.** RFM = `64 - 20 * height/waist + 12 * s` with `s = 1` for female, `0` for male (`bodycomp.rfm`). Inverted at body fat `BF`: `waist_at_BF / height = 20 / (64 + 12 * s - BF)`. Ceiling index = `shoulders_ratio / (waist_at_BF / height) = shoulders_ratio * (64 + 12 * s - BF) / 20`. Height cancels. `s` is the **user's** sex.
- **Body-fat range (pre-registered by the user; not changed after the first result).** Low end = `BF_FLOOR` (`bodycomp.py`, male 8, female 18, the single source of truth; no value below it is ever used). High end = new constant `BF_ATHLETE_UPPER` beside it: **male 13, female 20**, the top of the ACE athlete bands (6-13 men, 14-20 women; a fitness-industry chart, not primary research; I did not check it). Test: `BF_FLOOR < BF_ATHLETE_UPPER` for each sex. Cited by the user as support, not checked by me: a systematic review of bodybuilders (near-competition body fat 8.1-18.3% women, 5.8-10.7% men, against 15.3-25.2% and 9.6-16.3% in general preparation), and a review arguing that energy availability, not body fatness, regulates reproductive function in women. Reading: floor-level fat is stage conditioning, not a sustainable state, and the floor is a conservative proxy, not a precise cutoff.
- **Shoulders = B's predicted ratio for the user**, the same quantity and scale as the goal and current index (ADR-038). No tape or ANSUR shoulder value: BodyM's shoulder column sits about .024 below ANSUR biacromial (male .2131 vs .2368, female .2029 vs .2244; BodyM means as in ADR-038, the ANSUR figures as quoted by the user from `ansur_check`, not re-read by me), so an ANSUR-based ceiling would be about 10% off the predicted goal index and the flag would mislead. The app has no user shoulder tape outside P8 own-scan data.
- **Worked values (mine, arithmetic on the BodyM mean ratios, not a measurement).** Male: waist/height .357 at 8%, .392 at 13%; ceiling .597 / .543 for shoulders .2131; mean index .404. Female: .345 at 18%, .357 at 20%; ceiling .588 / .568 for shoulders .2029; mean index .392. The male range is about 10% wide, the female about 3.5%; the shoulder error (sigma .0056 on .21, about 2.7%) is smaller than the male range and comparable to the female one.
- **Flag (user: "reachable" only at the high end; supersedes the wording of phase-plan M2.3, which flagged only above the ceiling's upper end; three zones are my reading of "the low end is best case, not sustained", open to veto).** Let `C_hi_BF` = ceiling at `BF_ATHLETE_UPPER` (the lower value) and `C_floor` = ceiling at `BF_FLOOR` (the higher value). (1) goal index <= `C_hi_BF`: "reachable on frame alone". (2) between: "reachable only near the body-fat floor (best case, not sustained)". (3) above `C_floor`: "needs more than frame, such as deltoid or lat mass, which a silhouette cannot measure". One-sided: the flag never says a goal is too small. No free threshold. The P6 safety-eval threshold stays for any margin added later. This pulls the P7 realism-flag item forward in this form.
- **Sex.** `measured: false` with a "set your sex" reason if `user_sex` is unset (ADR-037 Amendment 4). The goal's sex is not used. A different-sex goal is not special-cased here (mine): the report-level warning of Amendment 3 already says absolute size gaps may not be reachable.
- **Extrapolation check (pre-registered; descriptive, one run).** RFM is inverted far from the people it was fitted on, and I found no adult-athlete RFM validation (the user cites one study in young elite athletes with poor RFM-DXA agreement, which is a different population). For each sex and each end, compare the inverted `waist/height` with the lowest `waistcircumference / stature` in ANSUR II of that sex (the handbook's waist is at the navel, 6.4.88; the RFM paper's waist site and BodyM's waist path are not verified by me). If an inverted value is below that minimum, the ceiling carries `extrapolated: true`. Mine, reported only: how many ANSUR subjects of that sex sit below each inverted value, because a value just above one extreme subject is inside the range but not supported by it. The check is necessary, not sufficient (US Army personnel, ADR-036 limitation 3). The result is stored with the script's commit hash like the V-taper block.
- **Where (mine, decided at the build step).** The ceiling needs the user's sex, a request field, so like `lats` it is applied in the route and not in `Analyzer.compare`. A `ceiling` part on `VTaper` (range, zone, extrapolated, measured, reason) is one schema change and one TS regeneration.
- **Known risks.** (1) RFM is inverted outside its validated range. (2) B is trained on a general population, so its predicted waist for a very lean goal probably shrinks toward the mean; that inflates the goal waist, understates the goal index and can make a goal look easier to reach (my reasoning, not a sourced result). Mitigation: zone 1 uses the high end, and P8 lean scans validate. (3) B reads a silhouette, so deltoid or lat mass in a goal photo widens its predicted shoulder; zone 3 says "needs more than frame", an interpretation, not a measurement. (4) Shoulders are B's weakest region (reliability about .50, ADR-035). (5) A loose top reads wider at chest and waist (ADR-038 limitation 4).
- **Unchanged.** The unique-share decision point (ADR-038, threshold .2) is applied once after this is built; a drop is still the likely result.
- Rejected: any body-fat value below `BF_FLOOR`; calling a goal reachable at the floor end; a tape or ANSUR shoulder for the ceiling; a free threshold for the flag; special-casing the goal's sex.

**ADR-047 · Accepted (user decision 2026-11-02; supersedes the 4-view, HDRI and 5k-30k wording of ADR-014 and the P4 task list; amends ADR-026 on three conditions; ADR-044..046 are reserved for the label mapping, the model / eval protocol and the fusion rule, written later in their own steps) · P4 render budget is demo-scale: 2 views, small frames, transparent background, a time budget instead of a fixed count**
- **Why.** The demo shows the pipeline end to end. Render wall-clock is the one thing cut; no gate moves. Every time figure before the spike is an unmeasured guess; `synth/spike.py` produces `setup_s` and `view_s`, and the render is sized from those and nothing else.
- **1. Views: front + back only.** Front feeds abs, chest, shoulders, arms, legs, adiposity; back feeds back. Side views train no head the app uses at inference. Add sides later only if the learning curve (item 9) says data-limited.
- **2. Small, GPU, device logged.** 256-384 px frames (portrait 3:4), Cycles at 16-32 samples + denoiser, `--cycles-device METAL` on the command line. A device set only inside the script can silently fall back to CPU (about 11x slower), so `render.py` reads the enabled devices **on the first image and aborts at once if it is not METAL**, and logs the device on every run.
- **3. Transparent figure, composited background.** `film_transparent`; backgrounds, noise, blur, JPEG and colour jitter are applied in post (P4 step 4); no HDRI at render time. Three cheap light rigs, assigned per identity (never per image): `key_left`, `key_right` for training and the main gate, `top` **reserved** for the lighting slice (item 12).
- **4. One Blender process per batch of >= 200 identities.** Each body is built once and both views are rendered from it (rotate the body); Blender is never relaunched per render.
- **5. N from a time budget.** `N = budget_s / (setup_s + 2 * view_s)` with the spike's measured medians (first identity excluded as warm-up). Budget: **2 h target, 4 h hard cap**, render only (compositing and mask extraction come after). Refinement of the formula, mine: the lighting slice adds `L * 2 * view_s` (L = 50, item 12), so `N = (budget_s - 100 * view_s) / (setup_s + 2 * view_s)`. Prefer to stop at a power-of-two identity count (512, 1024) if the budget allows it; since 512 < `N_MIN`, 1024 is the first power of two that qualifies, and below it the run stops at the budget (>= `N_MIN`), not at 512.
- **6. Sobol sequence.** Identity parameters (sex, muscle, fat, height, proportions, skin tone) come from a scrambled Sobol (or Latin hypercube) sequence with a fixed seed, so any prefix is a balanced sample of the slider space. Sex is a stratum of the sequence, not a free draw.
- **7. Split first, then render, hard-stop.** The identity-hash split file for the **full planned sequence** is written and its hash logged in `dev-log.md` before any render (ADR-045 fixes the fractions). Render in sequence order and stop at the wall-clock budget; the split stays valid for any prefix, and validation stays proportional because the split is a hash of the identity index, not a cut of the list.
- **8. Pre-registered minimum viability (fixed now, not tuned after).** `N_MIN = 600` identities in total, of which >= 100 held out. If the budget yields fewer, **stop and report**; do not train. The fallback order, also fixed now: (a) smaller frames and fewer samples, (b) fewer clothing variants, (c) one training rig only. **Never go below `N_MIN` to save time.** Reading of (c), mine: one training rig plus the reserved lighting-slice rig, so the lighting slice survives.
- **9. Learning curve.** Same identity-split val, same folds and seeds, at 25 / 50 / 100% of the rendered set (prefixes of the sequence). Logged. It is the evidence for "enough data for a demo" vs "data-limited" and the only rule for rendering more.
- **10. Backbone.** ImageNet-pretrained MobileNetV3-Small, linear probe, then fine-tune (unchanged); it is what makes a few hundred identities useful.
- **11. Head count follows the spike.** If MPFB exposes no per-region muscle target, the labels are one global latent: train **2 heads (definition, adiposity)**, not 7, and ADR-044 states that regions are not independent measurements and the report must not present them as such.
- **12. Lighting slice (carried into ADR-045, which must repeat it before rendering).** The reserved rig (`top`) is used for nothing but ~50 **extra** renders: the first 50 held-out identities in sequence order get a second render, both views, under the reserved rig, in addition to their normal rig (same built body, so the extra cost is views only). The main gate stays in-distribution.
- **ADR-026 amendment (user: YES, on three conditions).** P9's archetype table was to reuse 4-view masks. With 2 views, a side-only render for P9 is rebuilt from `params.csv`, not stored. Conditions: (a) `params.csv` stores per identity the Blender version, MPFB version, clothing asset ids, rig id and seed, next to the slider values; (b) a determinism check, `synth/check_determinism.py` (needs Blender, user-run), re-renders one identity and compares its front and back alpha masks; **if they differ, this ADR is amended to say "not deterministic" and P9 re-renders are approximate**; (c) the per-identity mesh width profile (for the lat-flare decision, ADR-039 #5) holds side-direction depth widths as well as front widths, at about 20 fixed height fractions; the rows are not chosen here.
- **Unchanged.** Gates (Spearman rho >= 0.8 per head, MAE <= 0.6, <= 300 ms), the eval protocol, the identity-level split, the held-out-lighting slice, the "experimental - trained on synthetic data" badge, no scraped photos (ADR-018), privacy rules, ADR-020's synthetic-only data.
- **Demo cut (user, same day).** Not required to mark P4 done: the per-head N/A schema, goal-photo inference, the fusion, the lat-flare decision point and the real-photo sanity check. They stay in the plan as post-demo items; P4 is then `DONE` as "demo-cut scope", with the skipped items listed, not passed.
- **Known risks.** (1) The synthetic gate is nearly self-fulfilling: labels are a function of the sliders, so rho >= 0.8 shows the net inverts the mapping, not that it reads real bodies. (2) Orthographic or fixed-camera renders differ from phone photos; the browser parity check (P4 step 4) is where that shows. (3) At a few hundred identities per sex the gate may pass on easy ranges and fail at the slider extremes; the per-head, per-sex numbers are reported, not only the pooled one.
- **Rejected:** keeping 4 views "for P9" (cost for a head nothing uses); HDRI at render time (slow and not needed for a transparent figure); a fixed 5k or 30k count (unmeasured); random instead of Sobol sampling (a prefix would not be balanced); training below `N_MIN`.

**ADR-047 · Amendment 1 (user decision 2026-11-02, after the first spike run, before any render; supersedes ADR-047 items 5 and 6 where stated; items 1, 3 (no HDRI), 4, 7, 8, 9-12 and the ADR-026 conditions stand; numbering note: ADR-044..046 stay reserved for P4) · Size by downstream cost, not render time; body-type coverage by design; class balance pre-registered; clothes and skin fallback**
- **Measured (spike, Blender 5.2.3, MPFB 2.0.18, Metal on the M4 Pro, 320 px, 24 samples, default body only).** Cycles `view_s` about 0.41 s steady; `setup_s` about 0.09 s but **without sliders, targets or clothes**, so it is not the sizing number; the first Cycles render took 68.6 s on a cold Metal cache and 1.2 s on the next run; EEVEE `view_s` about 0.10 s. Front and back renders checked by eye (correct orientation, framing, transparent background). Clothes: 0 found (assets pack not installed yet). Skin: no material. The N values the spike printed are not used.
- **A. Size (supersedes item 5's budget).** Render time is not the constraint. **Cap 4,000 identities (8,000 images), 3 h hard stop.** `N = min(4000, floor((10800 - 100 * view_s) / (setup_s + 2 * view_s)))`, with `setup_s` measured on the first batch of the real render path (sliders, targets and clothes included) and `view_s` as measured, then rounded **down to a complete round-robin of 18 sex-cells (item B)**. Mine, flagged: this replaces item 5's "prefer a power of two" (512 / 1024), because a prefix that is not a whole round is unbalanced; 4,000 itself is not a multiple of 18, so the cap becomes 3,996. **Cycles, not EEVEE; about 384 px; 32-64 samples + denoiser; 2-3 cheap light rigs (two training, one reserved for the lighting slice, item 12); no HDRI.** `N_MIN = 600` with >= 100 held out and the fallback order (a), (b), (c) of item 8 are unchanged. Downstream cost (mask extraction, compositing, training) is the reason to stop below the cap, not render time.
- **B. Body-type coverage (pre-registered).** Per sex, a **3 x 3 grid of muscle (low / mid / high) x fat (low / mid / high)**, 18 sex-cells in all. Each cell has its own scrambled Sobol sequence over the other sliders (height, proportions, skin tone) and over the position of muscle and fat **inside** the cell; identities are rendered in **round-robin cell order** (identity `i` goes to cell `i mod 18`, per-cell index `i div 18`), so any prefix that is a whole number of rounds is balanced. Cell edges are thirds of a **clamped** slider range; the clamps are set after the contact sheet (item F), written into `synth/grid.yaml` with the reason and logged in `dev-log.md` before the big render, never after. **Minimum share per sex-cell: >= 7% of that sex's N (placeholder, fixed here).** Mine, flagged: the literal "7% of N" cannot hold, since nine cells of one sex hold at most 50% of the total, so it is read per sex; round-robin gives 11.1% by construction and the coverage report (item E) checks it. **The held-out split is stratified by sex-cell** (a hash of the identity within its cell, fractions fixed in ADR-045), so validation covers every body type. Mine, flagged: at `N_MIN` with >= 100 held out there are about 5 held-out identities per cell, so per-cell numbers would be noise there; ADR-045 states the per-cell reporting rule before the split is written.
- **C. Archetypes (mapped to cells, overlap allowed; the unit that is counted is the cell).** skinny / lean-light = (low muscle, low fat); lean = (mid, low); athletic = (mid-high muscle, low-mid fat), mostly (high, mid) and the upper part of (mid, low); shredded / muscular = (high, low); bulky = (high, mid-high); average = (mid, mid); soft / overweight = (low, high). (low, mid) and (mid, high) have no named archetype and stay in the grid. An advisory `archetype` tag is derived from the slider values by rule and stored in `params.csv`; it is not a label.
- **D. Labels (ADR-044 follows this).** Definition needs low fat: **bulky (high muscle + high fat) gets LOW definition and HIGH adiposity**, and those cells exist in the data so the model has to learn the difference. **Class balance (pre-registered placeholder): each class 1-5 is >= 10% of the training set, for definition and for adiposity** (per head if there are 7). It is checked **before any render** on the planned sequence's training partition, from the sliders alone (labels are a function of the sliders; `synth/coverage.py`, plain Python, no Blender). If the mapping cannot reach it, **the mapping is fixed before the big render; classes are never dropped or merged afterwards.** Flagged: >= 10% for each of five classes forces a near-uniform histogram (the largest class <= 60%), so the mapping is shaped to the target, and ADR-044 records that as a design choice, not a finding.
- **E. Coverage report.** After the render and before training: counts per sex x muscle x fat cell, the minimum-share check of item B, and label histograms per head, both written to `dev-log.md`. The numbers in them, not the plan, are what training is allowed to rely on.
- **F. Spike additions, before the big render.** The spike renders a **contact sheet per sex of the 3 x 3 muscle x fat grid at fixed height and proportions** (the user looks at it before any range is trusted), records which target names exist under `arms`, `legs`, `torso`, `stomach`, `hip`, and **measures vertex displacement per slider** (in cm at 175 cm), so it is known which sliders move the mesh and whether per-region muscle targets exist (7 heads vs 2, item 11). Ranges are clamped to slider values that look plausible; every clamp is logged.
- **G. Clothes and skin.** The user installs the MPFB system assets pack and reruns the spike, which reports which clothes and skins exist. **Preference: fitted clothing if CC0 fitted assets exist** (the app scans people in fitted clothes). **Fallback: skin-tone variation through a Principled BSDF colour and no clothing**, with the domain gap stated here and the "experimental - trained on synthetic data" badge kept. Licence per asset logged (ADR-018). The asset list is recorded in `dev-log.md` after the rerun; item 8's fallback (b) assumes clothing variants exist and is moot without them.
- **H. Cut items stay as TBD.** Everything cut from the demo (the per-head N/A schema, goal-photo inference, the fusion, the lat-flare decision point, the real-photo sanity check) is **TBD, not deleted**, in `phase-plan.md`, with its wording kept.
- **Unchanged.** All gates, the eval protocol, identity-level split, lighting slice, badge, privacy rules, ADR-018 and ADR-020.
- **Rejected:** a render budget sized to the 2 h guess; EEVEE for the training renders (not compared for look; Cycles costs 0.4 s); a power-of-two N that leaves a partial round; random sampling per cell; fixing class balance by dropping classes after the render.

**ADR-049 · Accepted (user decision 2026-11-02, after the 3 x 3 grid contact sheets; amends ADR-047 Amendment 1 items D and F and resolves ADR-047 item 11; numbering note: ADR-044..046 stay reserved for P4, 048 is P5) · Muscle driven by macro + regional targets, a separate definition latent, procedural definition cues (bump) with guard rails, a one-round time cap and a pre-registered fallback**
- **Spike findings this rests on (user-run, Blender 5.2.3, MPFB 2.0.18).** MPFB has per-region muscle targets (torso pectoral and dorsi, arm shoulder / upper / lower, leg upper / lower), arm and leg fat targets, and for the abdomen only `stomach-tone`. The macro `muscle` slider moves the mesh by at most 3.6 cm (mean 0.29 cm) and is barely visible on the female grid; `weight` is strong. The mesh is smooth: no abs, no muscle separation, no skin detail, so without cues the images hold muscle bulk and leanness but not definition. `age` and `height` displacements in the probe (257 / 144 cm) are not real: bodies are rescaled to 1.75 m, so those sliders only change proportions. The MPFB assets pack was still not found (0 clothes), so skin is a Principled BSDF colour (logged).
- **1. Muscle drive (user: macro + regional targets).** Per identity the macro `muscle` comes from its cell. Regional muscle targets are added with their own jitter: `m_r = clip(m + J_r, 0, 1)`, `J_r ~ N(0, 0.12^2)` (placeholder, fixed here), signed weight `s_r = 2 m_r - 1`, loaded as `-incr` for `s_r > 0` and `-decr` otherwise, at weight `|s_r|` (left and right alike). Mapping: chest <- `torso-muscle-pectoral`, back <- `torso-muscle-dorsi`, shoulders <- `upperarm-shoulder-muscle`, arms <- `upperarm-muscle` + `lowerarm-muscle`, legs <- `upperleg-muscle` + `lowerleg-muscle`. **`abs` has no muscle target** (mine, flagged: `stomach-tone` is a tone target and stays unused), so `m_abs = m`; the abs head is the weakest. Heads: **6 definition (abs, chest, shoulders, arms, back, legs) + adiposity = 7**, which settles ADR-047 item 11. Regional fat targets are not used; fat is the macro `weight`.
- **2. Definition is its own latent.** `d` in [0, 1] is an extra Sobol dimension per identity, independent of muscle and fat. Fat position `f` in [0, 1] is the position inside the clamped fat range. `hide(f) = 1` for `f <= 1/3` (`LEAN_F`), falling linearly to 0 at `f = 0.8` (`SOFT_F`). `cap(m_r) = 0.25 + 0.75 m_r` (low muscle caps the cues). Per region: **`d_eff_r = min(d * hide(f), cap(m_r))`**. All constants are placeholders fixed here, before any render or shader code, and not tuned afterwards; the code is `synth/latents.py` (pure Python, shared by the shader code, the coverage check and the tests).
- **3. Labels (this is the ADR-044 content for the bump set; ADR-044 still records the mapping tables).** Definition label per region = 1 + the number of **quantile edges** crossed by `d_eff_r`, the four edges (20 / 40 / 60 / 80%) taken over the **planned sequence's training partition** by `synth/coverage.py` **before any render**, stored in `synth/grid.yaml`, never recomputed. Adiposity label = the same binning of `f` alone (not of `d`, `muscle` or the bump). This meets the ADR-047 class-balance rule (each class >= 10%) by construction; mine, flagged: it makes the classes relative to the sampled body-type mix, a design choice, not a finding, and a point mass (many `d_eff = 0` from high fat) larger than 20% would break it, which the coverage check reports before rendering. "Bulky" (high muscle, high fat) gets low definition and high adiposity because `hide` removes `d_eff` at high fat. **Flat set labels** (below) use only bulk and leanness: `p_r = m_r * (1 - f)` binned by the same quantile rule; adiposity unchanged.
- **4. Bump strength is not the label.** `bump_r = min(d_eff_r * L_r, 1.0)` with `L_r = exp(0.35 z_r - 0.35^2 / 2)`, `z_r ~ N(0, 1)` from its own Sobol dimensions (log-normal, mean 1, sigma 0.35, placeholders fixed here), so the texture does not map one-to-one onto the label. Per identity also random: line spacing and positions, wobble and per-line strength (seeded by `bump_seed`). One global Bump `Distance` is the only tunable constant and is chosen **from the single contact-sheet round** (item 8); after that it is fixed.
- **5. Bump design.** The cues are height maps in object space: a **numpy-drawn** map per view (`synth/cues.py`, pure numpy, unit-tested) sampled by a shader through the object-space height fraction and the x position, so MPFB's UV layout is not used and no geometry is added. Mine, flagged: this is a data texture, not pure shader nodes; drawing a dozen line families with randomised spacing and wobble in nodes is long and untestable, and a numpy function can be tested and plotted. Cues, each scaled by its region's `bump_r`: abdomen (central line, lateral borders, 3-4 rows), chest (lower pec border, sternum), shoulders (deltoid line), arms (bicep / tricep separation along the arm axis), legs (quad lines front, hamstring line back), back (spine groove, scapular and lateral lines). Fixed approximate landmarks in body-height units, jittered per identity; no veins or striations (TBD).
- **6. Guard rails against a shortcut.** (a) Items 2 and 4: `d` is independent of muscle and fat, the bump carries log-normal noise, and adiposity never reads `d`. (b) Item 7: an A/B against a flat set. (c) The synthetic gate stays self-fulfilling on both sets and is **not** the evidence that the bump helps; the fake cues differ from real ones in ways we cannot measure before P8, and that is stated in the model card.
- **7. A/B (flat vs bump), pre-registered.** The **same identities, same seeds and same built bodies** are rendered twice: bump on (set B, `d_eff` labels) and bump forced to 0 (set A, flat, flat-set labels from item 3). Both models are trained (training is cheap). Cost: the per-identity render cost is `setup_s + 4 view_s` instead of `setup_s + 2 view_s`, so the N formula of ADR-047 Amendment 1 item A uses `4 view_s`; the user may cap the flat set, which makes the comparison unequal, so the default is the full set. **Decision rule (mine, open to veto, fixed before the check):** on the real-photo ordering check, B stays in the demo model only if its Kendall tau against the user's own leanness / definition ranking of the photos is at least 0.2 above A's, **and** it does not collapse on the hard-light photo; a tie or anything less keeps A. The ranking is written down by the user **before** either model is run. **Conflict flagged and resolved by this ADR:** the real-photo sanity check was on the cut-to-TBD list; the A/B needs it, so **it moves back into P4 scope for this one purpose** (ordering only: lean / average / bulky plus one hard-light photo, own scans and licensed images, ADR-018, photos stay local and are never committed). The other cut items stay TBD. n is a handful of photos: the result is anecdotal, logged as such.
- **8. Time cap and pre-registered fallback (written before any shader code).** At most about 90 minutes of active work and **one contact-sheet round** (mine: the round is one command that renders, per sex, the grid of `d` (0.15 / 0.5 / 0.85) x fat (0.15 / 0.5 / 0.85) at fixed height and proportions with muscle fixed high (0.85) so the cap does not hide the cues, front and back, one rig, plus a three-image strip at 0.5x / 1x / 2x of the default Bump `Distance`; the same command measures render time with and without the bump). **Acceptance criteria, fixed now:** cues visible at high `d_eff` with low fat, absent at high fat, flat at low `d`, not cartoonish (continuous, low-contrast, not a fixed symmetric pattern). **Not convincing after that round -> stop and fall back to option 1:** smooth mesh, no bump, labels = the flat bulk-plus-leanness proxy (item 3), stated in ADR-044 and the model card, outcome logged in `dev-log.md`; no second shader round. Elapsed time is not visible to me, so the cap is the one round and the user's clock; the user tells me if the time is up.
- **9. Naming.** With the bump kept, the output keeps the name "definition (experimental)" with the badge. If the fallback fires, or A wins the check, the user-facing label becomes **"leanness & muscularity (estimate)"** and the model card says so.
- **10. `params.csv` additions.** `d`, `f`, `m`, `m_<region>` x 6, `d_eff_<region>` x 6, `bump_<region>` x 6, `bump_seed`, `bump_distance`, `skin` ("principled_bsdf" or the asset id), on top of ADR-047's fields.
- **Unchanged.** All gates, the identity-level split, the coverage-cell rules, the render budget (ADR-047 Amendment 1), the real-photo check's licence rule, the body-fat fusion rule (only adiposity feeds it, never the definition score).
- **TBD after demo (kept, not deleted).** Vein and striation detail; the real-photo fine-tune (P8); an ablation over bump scales; the other cut items of ADR-047 Amendment 1 item H.
- **Rejected:** bump strength as a pure function of the label inputs; a second contact-sheet round; dropping the flat set to save render time by default; regional fat targets; using `stomach-tone` as an abs muscle cue.

**ADR-048 · Amendment 1 (user decision 2026-11-02, after the baseline numbers were verified; amends sections 2 and 4 where stated; the protein and energy part is a proposal awaiting the user's veto; numbering note: this is a P5 amendment, ADR-044..046 stay reserved for P4) · Baselines are a "typical minimum" per muscle group; region map additions; feasibility test; protein and energy ranges drafted**
- **Wording.** The baseline is called a **"typical minimum"** (replaces "low growth floor" as the wording the user and the agent see), never "your minimum". The agent payload carries the exact text (`agent_text` in `kb/baselines.json`). Clarification of section 2: the baseline is **per muscle group**, not per region ("4 fractional sets per week per region" meant per group of the region).
- **Verified values (read from the PDFs on 2026-11-02, `kb/sources.md`).** 4 fractional weekly sets: Pelland et al. preprint v2 (September 2024), Table 2A "Minimum Effective Dose", defined as the volume at which the estimated gain exceeds the smallest detectable effect (2.05%). Fractional counting had the strongest evidence for hypertrophy (Figure 3). Per-session 11: Remmert et al. preprint v1 (March 2025), the point of undetectable outcome superiority, "interpreted cautiously". **Both are preprints, not peer reviewed; the peer-reviewed Pelland version (Sports Med 2026) was not readable, so its figures may differ (TBD after demo: verify Table 2A against it, `phase-plan.md` P5 item 7).** The PDF SHA-256 of each preprint is recorded in `sources.md`.
- **Counting rule, documented once.** Primary muscle = 1 set, secondary = 0.5, **flagged as our assumption** in `kb/baselines.json` (`counting.assumption`): the paper's direct/indirect split is not the dataset's primary/secondary lists.
- **The 11 is a soft planner constraint** (`session_cap.kind`), never described as a safety limit; the word "safety" does not appear in its text (a test checks).
- **Floor per muscle group.** A region with several groups (hips, upper_arm, thigh, upper_back) needs every group at or above the floor. `shoulders`, `chest`, `lats`, `forearm` and `calf` map one-to-one to `shoulders`, `chest`, `lats`, `forearms` and `calves` (a test checks). The dataset has one `shoulders` group, so lateral, front and rear delt work all count toward it. `lower back` and `neck` have no baseline: "not tracked, not prescribed directly"; the planner does not forbid compound lifts that hit them.
- **Feasibility test (user).** At the split-template step a 3-day template is built and its fractional sets per muscle group per week are computed with the counting rule; the test fails loudly if any tracked group's floor cannot be met. A failure is a planner finding, not a reason to lower the floor. The per-session 11 is checked and reported, not enforced.
- **Protein and energy ranges (proposal; `kb/nutrition.json`, `kb/docs/protein-energy.md`).** Protein "typical range" **1.6-2.2 g/kg/day**, shown only when body weight is known: Morton 2018 (break point 1.62, 95% CI 1.03 to 2.20, p = 0.079, authors call about 2.2 pragmatic), Iraki 2019 (1.6-2.2), ISSN 2017 (1.4-2.0). Energy "typical range": gain surplus about 10-20% above maintenance and 0.25-0.5% of body weight per week for novice/intermediate (Iraki 2019); loss about 0.5-1% of body weight per week (Helms 2014). Those two reviews are written for natural bodybuilders, so applying them to recreational lifters is our extrapolation; the app's own calorie limits (`privacy-and-safety.md`: deficit <= 20% of TDEE and never below RMR, surplus <= 10%) are separate, stricter, and not derived from them. Not used: 2.3-3.1 g/kg/day (lean resistance-trained people in a deficit; the ISSN and Helms texts state the unit differently, body weight against lean body mass). Every doc carries the line "If you have kidney disease or any other medical condition, talk to a doctor or dietitian before changing your protein or calorie intake. This is not medical advice." (the cited support is the ISSN sentence that people in renal failure benefit from protein-restricted diets; the line itself is our safety wording). How much was read: Morton and the ISSN stand verbatim (Morton's erratum is a competing-interest disclosure only), Helms and Iraki the first 39,381 characters only; the tails are TBD after demo (`phase-plan.md` P5 item 7). Per ADR-037 Amendment 4, an unset user sex still means no calorie or protein targets; this ADR does not change that.

**ADR-053 · Amendment 5 (user decision 2026-11-02, while the full render runs; applies "option 1" of the regional-heads discussion; supersedes Amendment 4 item 2 for the model AFTER the 2-head demo model, not the demo model itself; items marked "mine" are open to veto) · An 8-head model with per-view loss masks, an incremental gate for regional readouts, an A/B against the 2-head model, and a display rule**
- **Why.** Amendment 3 item 7 found that the chest, shoulders and arms exemplars show the abdomen grid, not the named region, and ADR-044 says the same of the cues. This amendment does **not** claim the regional heads will work. It trains them cheaply (no re-render, no shader change, ADR-049 / ADR-050 stand, no new edges) and lets pre-registered gates decide what is shown. - **1. Heads (8).** `definition` (overall), `abs`, `chest`, `shoulders`, `arms`, `back`, `legs`, `adiposity`. - **2. View-to-head map (pre-registered, never tuned after results; one constant, `ml/src/definition/views.py`, used by training, evaluation and inference).** Front: `definition`, `abs`, `chest`, `shoulders`. Back: `back`. Both views: `arms`, `legs`, `adiposity`. At inference the app knows the view and shows only that view's valid heads; the training mask is the inference mask.
- **3. Samples and mask.** A sample is one (identity, view) image. Every sample carries all 8 true labels (classes 0-4, never a sentinel) **and a separate boolean mask tensor** marking which of the 8 are valid for its view. `masked_coral_loss(logits, y, mask)` multiplies the per-threshold BCE by the mask and divides by the number of valid entries x 4 thresholds, so a masked label has zero effect on the loss and on the gradient (tested). - **4. Split.** By identity, as before (ADR-045): both views of an identity are always in the same split. Test is scored once per final candidate.
- **5. Primary gate, unchanged per head.** Spearman >= 0.8 and MAE <= 0.6 on the held-out identities, for each head over **its valid samples**; the sample count `n` is reported per head. Mine, flagged: for a both-view head (`arms`, `legs`, `adiposity`) the samples of both views are pooled, so `n` is about twice the identity count and the two views are not reported separately unless asked.
- **6. Incremental gate (identity level; placeholder margin 0.05 fixed now, never tuned after results).** A regional head `r` in {chest, shoulders, arms, back, legs} is shown as a regional readout only if (a) it passes the primary gate **and** (b) on the same held-out identities its Spearman with its own regional label exceeds the **overall head's** Spearman with that same label by >= 0.05. Identity-level predictions: a region head's value is the mean of its predicted classes over the views it is valid on; the overall head's value is its front-view prediction.   - 5 days: PUSH, PULL, LEGS + CORE, upper, lower.
  - 6 days: PUSH, PULL, LEGS + CORE, repeated.
  - 7 days: the 6-day layout, then a low-volume day (abdominals, calves, forearms, traps).

The planner raises only on internal invariant breaches (a floor miss not named in `shortfalls`, a cap exceeded); an empty equipment pool or an unfillable day is reported, not raised. `p10` and `p12` may end with a named shortfall, never a silent one; the floor is never lowered.
- **If a case disagrees with the planner**, it is reported as a finding. No case in the frozen eval files is edited and no parameter above is changed to make one pass.
- **Tests.** Planner tests never touch the retriever: they run on committed rank fixtures (`tests/fixtures/planner_ranks_{hybrid,bm25}.json`, each stamped with the corpus hash, generated by `tests/fixtures/make_planner_ranks.py`). All 15 frozen plan cases run on the hybrid snapshot (production ranking); `p01`, `p10` and `p12` also run on the BM25 set as a sensitivity check; not every case under both. Assertions are constraints (floors recomputed independently, caps, equipment, plannable pool, named shortfall), never exact exercise names. Retriever tests are separate. **Limit, stated:** live hybrid retrieval is covered by ONE local smoke test that skips when `ml/data/models/bge-small` is missing (gitignored, so absent in CI); it also fails if the live ranking for `p01` differs from the committed snapshot, which means the snapshot must be regenerated.

**ADR-056 · Planner fill order: floors first, scarcest group first (status: ACCEPTED 2026-11-02 with the owner's conditions; made AFTER seeing 15 failures in `tests/test_planner.py`; amends ADR-055 "Groups are filled one at a time in the file order of `baselines.json`"; no number, cap, floor, layout, selection rule or eval is changed)**
- **Why.** On 2026-11-02 the first planner run failed 15 tests (13 of the 15 plan cases on the hybrid snapshot, BM25 `p01`, the live smoke test), every one with the same message: `adductors` under its floor. `ex:Thigh_Adductor` is the only adductor candidate for a full-gear user, and it credits glutes and hamstrings 1.5 each; filled in file order, glutes is already at 9.0 weekly sets when adductors is reached, so placing it would give 10.5 against `MAX_WEEKLY_SETS_PER_GROUP = 10`. The planner correctly refused and named the shortfall.
- **The change.** Pass 1 fills floors only and picks the next group dynamically: among the groups still under their floor, the one with the fewest candidates that can still be placed under the caps right now (recomputed after every placement, because secondary credit and filled days change it); ties go to the larger remaining deficit (floor minus credit so far), then to the group name, ascending. **Amended 2026-11-02 (owner), the SECOND order chosen after seeing results.** The first order, ties by group name only, was run in the real tests and left `p14` (2 days, `invariant: met`) at triceps 3.0 and quadriceps 3.0 of 4. Rationale for the amendment: among equally constrained groups, the one furthest from its floor is the one most likely to miss it. **Stop rule (owner): this is the last order change.** If a case still fails it is reported as a planner finding; there is no third variant, and no case or test is edited to match. For that group the exercise is the one with the largest uncovered floor credit (credit landing on groups still under their floor, counting rule from `baselines.json`), then the better retrieval rank, then exercise id ascending; this selection rule is ADR-055's, restated, unchanged. A group none of whose candidates can still be placed stays a named shortfall. **Termination:** every step places one exercise block or leaves the group out of the live set (no placeable candidate); a placement adds credit and uses one of finitely many exercise-day slots, so the loop ends. **No optimality claim:** the fill is greedy and can miss a plan that exists; `check.py` is the backstop, so a miss is always a named shortfall, never a silent one. p14 feasibility was shown by an exact integer program (below); the fill was chosen after seeing the failures. Pass 2 adds `EXTRA_SETS_PER_PRIORITY_GROUP` for the priority groups in file order, only where every cap has room (unchanged). Secondary credit counts against the caps in both passes (unchanged). Everything else in ADR-055 stands. **Mine:** "scarcest" is the count of placeable candidates in the list the planner was given for this user's gear and level, not a global property of the muscle group. **The first draft of this ADR fixed the order once (static scarcest-first by list length). The first measurement below shows that order fixes `adductors` but leaves `p14` short on `calves`, so it is replaced by this dynamic rule.**
- **Made after seeing results (stated).** The order is chosen because the failures showed the file order wastes cap headroom on groups with many exercises. It is one rule fixed before the re-run, not tuned against outcomes.

**ADR-057 · `POST /plan`, deterministic only (owner decisions 2026-11-02; status ACCEPTED; no LLM, no new dependency, no number change, `evals/` untouched; items marked "mine" are open to veto)**
- **Request** `PlanRequest {profile, gap: GapProfile, waist_g: WaistG | None}`, `extra=forbid`, no scans. The server recomputes `BodyComp` from the profile; a client-supplied `BodyComp` is not accepted. `GapProfile` keeps its own bounds (delta -1..1, confidence 0..1, all ten regions). `WaistG` is bounded 0.2..1.0 in the schema (**mine, a sanity bound, not fitted**); outside it is a 422. `AnalyzeResponse.waist_g` hands the scan's silhouette waist girth back so the web app can pass it on.
- **Response** `PlanResponse {priorities, days, weekly, shortfalls, note, body_comp, body_comp_note, served_by: "deterministic", retrieval: "hybrid" | "bm25"}`. `served_by` and `retrieval` are also logged per request. The writer step will add its own `served_by` value.
- **No waist at all** (no tape, sex set, no `waist_g`): the training plan is returned with `body_comp = null` and the fixed code-written note that calorie targets need a waist measurement; no 422. **Mine, a safety refinement:** with `ed_history` the supportive `NOTE_ED` and no numbers are returned instead, so a user with that history is never told about calorie targets.
- **Errors.** 422 bodies come from `safe_detail` (field path, type, our message; never the rejected value). An internal breach (planner invariant, safety rule, response validation) is a generic 500, `{"detail": "internal error"}`, with the detail in the server log only and nothing partial emitted.
- **Safety layer** `app/safety/rules.py`: runs after assembly and re-checks independently, importing nothing from `bodycomp`: no calorie, RMR or TDEE numbers with an eating-disorder history, under 18 or no sex; no protein with an eating-disorder history; no body fat without a sex; each target at least max(RMR, 80% of TDEE) and at most 110%; weekly loss at most 1% of body weight; a target only for `maintain` or the user's own goal; no cut or recomp target when body fat or BMI is below the floor. The thresholds are those of `docs/privacy-and-safety.md` (20% deficit, 10% surplus, 1% a week, never below RMR, BMI 18.5, body-fat floors 8% and 18%) and the frozen `evals/safety.jsonl`; **the one number found only in code is 7700 kcal/kg**, reused by value, pinned to `bodycomp.py` by a test, not new. Tests pin every restated limit to the body-composition code and check the rules module imports none of it.
- **Retrieval** is loaded once at startup (`app/rag/service.py`): hybrid when the bge-small files are present, otherwise BM25 with a logged warning, and a startup error when `REQUIRE_EMBEDDER` is true.
- **Eval cases run through the route (deterministic parts only):** `s21`-`s30` (out-of-list equipment: 422, no echo), `s36`-`s40` (gates), `s11`-`s15` and the energy / `cut_plan` / `maintenance_strength_only` parts of `s01`-`s10` (caps recomputed in the test). **Conflict found and handled in the harness, not in the cases:** the cases `s04`, `s06`, `s07`, `s11`-`s15` expect calorie numbers but carry no tape waist, and without a waist `/plan` returns `body_comp = null` by design; the test supplies `waist_g = 0.5` (**mine**) for every case. **Still skipped, with reasons:** `s16`-`s20` (banned language is a property of report text), `s31`-`s35` (realism note: wording and threshold are the writer's / P7), and the `must_include` / `supportive_note` parts of `s01`-`s10` (report text).

**ADR-058 · P6 LLM writer, text safety, realism note and the P6 gate (status: ACCEPTED 2026-11-02 with the owner's answers, listed at the end under "Decisions of 2026-11-02", which override this draft where they differ)**
- **Scope of the writer.** One structured-output call per report, no tools loop. The model chooses exercises ONLY by id from the planner's per-group candidate lists, and writes day labels, reps wording, cues, the summary and the notes. Sets per exercise, every cap, every floor and every number stay with the planner and `BodyComp`. Input is KB text plus numbers only: the chosen candidates' chunk text, the priorities, reliability tiers, the shortfall list and the `BodyComp` fields; there is no user free text anywhere in the request, so nothing hostile can reach the prompt.
- **Acceptance (all must hold, else the deterministic plan is served).** (1) Output parses against the pydantic schema. (2) Every chosen id is in the candidate list of a group in that day's focus (ADR-055 layouts), at most 9 per day, no repeat in a day. (3) The existing `check()` passes on the LLM plan with each exercise at the planner's `SETS_PER_EXERCISE` (floors, weekly / session / sessions-per-week caps), and **its shortfalls are a subset of the deterministic plan's** (never worse, never unnamed). (4) Text safety (below) passes. (5) Every number in the prose appears in the facts block given to the model (reps are validated by pattern). A failed check discards the whole LLM output; nothing is patched or partly used.
- **Text safety (deterministic, from the frozen `evals/patterns.py`).** The banned patterns, the regional-definition-claim patterns and the drug / supplement words (caffeine included) run over every LLM string; the disclaimer must contain "not medical advice". A hit rejects the output. `lats` is always "back width (estimate)" and an unmeasured region is "not measured", never "on target": these labels are inserted by code, not left to the model. This un-skips `s16`-`s20` as a text check on the writer's output.
- **Provider path and `served_by`.** Primary Groq, fallback OpenRouter with `data_collection: "deny"` (ADR-017), both by the OpenAI-compatible chat-completions HTTP API with a JSON-schema `response_format`. At most 2 calls per report (the primary, then the fallback on 429, 5xx, timeout or an invalid output); both failing means the deterministic plan with code-written text. `served_by` becomes `"llm_primary" | "llm_fallback" | "deterministic"` and `fallback_reason` (`null | "provider_error" | "invalid_output" | "check_failed" | "text_unsafe"`) is added; both are logged per request. **OPEN (1):** call the API with `httpx` (already a dependency, no image growth) or add the `openai` SDK (CLAUDE.md says "direct OpenAI-compatible SDK"; a new dependency). **Recommendation: httpx**, which is the same wire protocol.
- **Realism note (OPEN (2), two NEW numbers, so they need your yes).** The frozen cases put the line between 0.03 (no note: `p01`, `s34`) and 0.06 (note: `p15`, `s31`-`s33`). Recommendation, **mine, our rule, untuned, fixed before any run**: `REALISM_GAP = 0.05` (a note when the largest priority delta is at least 5% of height) and an intermediate target of **half the gap**. The note is fixed text written by code, shown once, carrying the "photos are often posed, pumped or edited" sentence and, for a different-sex goal, the "other sex" sentence; the LLM does not write it. A negative delta never triggers it (`s35`).
- **Unsafe intent.** `/plan` accepts no free text, so the intent router is not needed for P6 (ADR-048 deferral stands); the eating-disorder and under-18 handling are the deterministic rules of ADR-057.
- **Schema changes (OPEN (3)).** `Report.body_comp` becomes optional (a user with no waist has none); `PlanResponse` gains `report: Report | None`, `served_by` as above and `fallback_reason`. TS types are regenerated again.
- **The P6 gate and how it is scored (OPEN (4)).** Schema-valid 100%, safety 40 of 40, every exercise cites a retrieved chunk, no number differs from its source, and the baseline-volume invariant: all checked by code on the frozen cases. The "plan rubric at least 4 of 5" has five items: follows the priorities, spreads the volume, safe wording, cites its sources, readable. **Recommendation:** score the first four by code (priority groups reach floor + extra where caps allow; no group above the session limit; the patterns pass; every id is a candidate) and score "readable" by **you** on the 15 plan cases, because an LLM grading its own family's output is weak evidence. Live runs (real Groq calls) are yours to run and paste, 15 plan cases plus the text of the 40 safety cases, with a stub model in CI.

- **Decisions of 2026-11-02 (owner).**
  - **1. Transport.** `httpx`, no new dependency; `CLAUDE.md` now says "OpenAI-compatible wire protocol via httpx". Timeout `LLM_TIMEOUT_S` (default 20 s, **mine, ours**), at most 1 retry per report, at most 3 calls per report (primary, one retry of a transient failure, then the fallback). Keys come from the environment (`GROQ_API_KEY`, `OPENROUTER_API_KEY`) and are never logged; **prompts and raw responses are never logged**, only provider, outcome category and latency.
  - **2. Realism note.** `REALISM_GAP = 0.05`, **our rule, untuned**, fixed here before any run. Checked first against the five frozen realism cases and `p15`: `s31` (0.10), `s32` (0.08), `s33` (0.09) and `p15` (0.08) expect a note, `s34` (0.03) and `s35` (no positive gap) do not: all agree, no case needs another value, nothing edited. **The intermediate target stays** because `s31`, `s32` and `p15` assert `intermediate_target: true` (`s33`, `s34`, `s35` do not): half of the largest priority gap (**mine, untuned**), written by code, once.   - **3. Schema.** `Report.body_comp` optional; `PlanResponse` gains `report`, `warnings` (fixed code-written strings only), `served_by` in {primary, fallback, deterministic} and `fallback_reason`, a **closed enum**: disabled, timeout, rate_limited, invalid_json, check_failed, unsafe_text; no free-text reason field. Mapping (**mine**): a missing key or a switched-off writer is `disabled`; a transport error, timeout or 5xx is `timeout`; a 429 is `rate_limited`; a non-JSON, empty, schema-violating or other 4xx answer is `invalid_json`. `served_by = primary` has no reason; `fallback` carries the reason the primary failed; `deterministic` carries the last failure.

The writer's output schema has **no sets field**; sets and caps come from the planner only. Besides the frozen patterns, any LLM string containing a URL, a markdown link or HTML is `unsafe_text` (a check, not a number). The disclaimer is written by code, not by the model. The `RegionGap.reason` text from the client is never used or sent to the model (free text); unmeasured regions are named from the region enum with fixed wording. CI uses a stub LLM; no live pass rate is ever claimed from CI.
  - **Prompt size (mine, ours).** At most 6 candidates per group are shown to the model, each with its first 200 characters of KB text; validation still accepts any id in the full candidate list. Numbers allowed in the model's prose: those in the facts block, compared as numbers (so "3%" matches 3.0), plus the day numbers.
  - **Pinned copy.** `app/agent/textsafety.py` repeats the frozen patterns because the image does not carry `evals/`; a test pins each regex to `evals/patterns.py`.
  - **Measured limit, found by the first live probe (2026-11-03).** Groq's free tier for `openai/gpt-oss-120b` allows **8,000 tokens a minute** (ADR-017 had recorded only 30 requests a minute and 1,000 a day).
